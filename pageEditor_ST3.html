Feedback Page

Technical Description

The feedback page is built using the shared template that Student 1 made, so the header, nav bar and footer are the same across all pages. I linked the global styles.css for the base styling, and then I added my own page-specific CSS inside a style tag in the head section so it only affects this page and doesnt interfere with anyone elses pages.

For the HTML structure I used semantic elements like section tags to split the page into three clear parts — the programme directory, the ratings and reviews area, and the feedback form. The form itself uses two fieldset elements with legend tags to group the personal details and the feedback details separately, which helps with both readability and accessibility.

The programme directory at the top uses a scrollable container. I set a max-height on a div and used overflow-y: scroll so that users can scroll through the programme cards without the page getting really long. Each programme card uses flexbox (display: flex with gap) to lay the image and text side by side (MDN Web Docs, 2025). I also used object-fit: cover on the images so they stay the same size regardless of the original image dimensions.

The reviews section uses CSS Grid with repeat(auto-fit, minmax(260px, 1fr)) which means the cards automatically wrap onto new rows depending on the screen width (MDN Web Docs, 2025). I didnt need any media queries for this part because auto-fit handles the responsiveness on its own which I thought was quite neat.

For JavaScript, I wrote two main bits of functionality. The first is a character counter that listens for the input event on the comment textarea and updates the remaining character count in real time. The second is the form validation function which checks that the name, email, and comment fields arent empty, and also checks that the email contains an @ symbol (W3Schools, 2025). If validation fails it shows error messages below the relevant fields by toggling the display property. If everything is valid, it hides the form and shows a confirmation box instead.

Accessibility

I tried to make the feedback page as accessible as I could. Every form input has a label element linked to it using the for attribute, which means screen readers can properly announce what each field is for. I used fieldset and legend to group related inputs together so its clear which fields belong to personal details and which are for the feedback itself. The error messages are placed right next to the fields they relate to so users can easily see what needs fixing. The nav bar has an aria-label="Main navigation" which helps assistive technology identify it. All images have descriptive alt text too.

Team Page

Technical Description

The team page follows the same shared template as the other pages. I used the global styles.css and then added page-specific styles in a style tag in the head, same approach as the feedback page.

The layout is a CSS Grid using repeat(auto-fit, minmax(220px, 1fr)) so the member cards automatically arrange themselves based on screen size. Each card is a div with overflow: hidden and a border-radius to give it a rounded look. The member photos use object-fit: cover with a fixed height of 220px so they all look consistent even if the original images are different sizes.

The main interactive feature is the expandable details panel on each card. I did this entirely with CSS — no JavaScript at all. Each card has a hidden div (member-details) that has max-height: 0 and overflow: hidden by default. When the user hovers over the card or focuses on it with the keyboard, the max-height transitions to 200px which creates a smooth slide-down animation. I used a transition on both max-height and padding so it looks smooth rather than just snapping open.

I also added transform: translateY(-6px) on hover so the cards lift up slightly, which gives a nice visual feedback to show which card youre looking at. The whole thing works without JavaScript which keeps the page lightweight and means it still works even if someone has JS disabled in their browser (Duckett, 2011).

Accessibility

Since the expand effect relies on hover, I needed to make sure keyboard users could access it too. I added tabindex="0" to each member card so they can be focused using the Tab key, and the CSS uses :focus alongside :hover to trigger the same expand animation. This means you can tab through all four cards and see the details without needing a mouse. Each image has alt text that includes the persons name and student number. The nav bar also has the same aria-label as the other pages for consistency.

Content Page

Technical Description

My content page is about SDG 13: Climate Action (United Nations, 2025). Its structured into five sections — an introduction, why it matters, what students can do, real life examples, and useful resources. Each section has its own id attribute so users can jump to them from the internal navigation at the top of the page.

For the layout, each section is wrapped in a div with a class called content-section which gives it a white background, rounded corners, padding and a subtle box-shadow. This makes each section look like a card which I think makes the page easier to read compared to just having a wall of text. The images use max-width: 100% so they scale down on smaller screens without overflowing.

The internal navigation at the top uses a nav element with anchor links that point to the section IDs (like #intro, #why, #students etc). I styled the nav list with flexbox and flex-wrap so the links sit side by side and wrap onto new lines if the screen is too narrow. Theres no JavaScript on this page at all.

I also added a "Go to Top" button that stays fixed at the bottom-right of the screen using position: fixed. It links to an id="top" on the body tag. I gave it a large border-radius (999px) to make it circular and styled it with the same green colour used across the site (#315c4b). Its purely HTML and CSS — no JavaScript needed.

Accessibility

The content page has two nav elements — the main site navigation and the internal page navigation — and I gave each one a different aria-label so screen readers can tell them apart ("Main navigation" and "Page sections"). All four images have descriptive alt text explaining what the image shows. The Go to Top button has an aria-label="Go to top of page" so its clear what it does even if you cant see the arrow symbol. I used semantic heading levels (h1 for the site name in the header, h2 for section headings) to keep the hierarchy correct.

Challenges and Lessons Learned

1. Getting the CSS-only expand to work on keyboard: The hover effect on the team cards was straightforward enough, but I realised that keyboard-only users wouldnt be able to see the hidden details. I had to learn about tabindex and how :focus works in CSS. Once I added tabindex="0" to each card and included :focus in the CSS selector alongside :hover, it worked. This taught me that you always need to think about how people without a mouse will use your page.

2. Form validation error messages: I initially had all the error messages showing at once which looked messy. I had to figure out how to hide them by default with display: none and only show the relevant ones when validation fails. I also had to make sure they reset properly if the user corrects a mistake and submits again. It took a few tries to get the logic right but I learned a lot about DOM manipulation from it.

3. The scrollable programme directory: I wanted the programme cards to be inside a scrollable box so the page doesnt get too long, but at first the scroll container wasnt showing properly because I hadnt set a max-height. Once I added max-height and overflow-y: scroll it worked. I also had to make sure the cards inside still looked right with flexbox — getting the image to stay a fixed size while the text flexes was a bit fiddly at first.

4. Keeping page-specific CSS separate from the global stylesheet: Since Student 1 created the shared styles.css, I didnt want to edit it and risk breaking other peoples pages. So I put all my page-specific styles inside a style tag in the head of each page. This way my styles only apply to my pages and dont affect the rest of the site. It took me a bit to understand the best way to scope CSS without using something like SASS but this approach seemed the simplest and cleanest.

Compliance

I have tried to make sure all my pages comply with JANET regulations. None of my pages contain any illegal, offensive, or inappropriate content — everything is related to SDG 13 Climate Action and is educational in nature. I have not included any copyrighted material without permission; the images used are either free-to-use or provided for the coursework, and any external links (like the UN Climate Change site) are properly attributed.

The feedback form on my page does not actually send data anywhere — its purely a front-end demonstration with JavaScript validation. No personal data is collected, stored or transmitted to a server, so there are no data protection concerns. If this were a real form I would need to consider GDPR and make sure users consent to their data being stored, but since its just a coursework demonstration that isnt applicable here.

All pages include proper attribution in the footer showing my name, student ID, and role. The shared template and CSS are credited to Student 1. I have also made sure that the content is suitable for a university website and would be appropriate for anyone to view.
